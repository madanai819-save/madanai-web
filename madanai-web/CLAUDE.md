# madanai-web — 新規ブログ記事作成時のチェックリスト

このサイトはビルドツールなしの静的サイト（全HTMLファイルが header/footer/CSS/script を含む完全自己完結型）。新しいブログ記事を1本作成するたびに、**以下をすべて実施すること**（ユーザーから都度指示がなくても必須）。

## 0. コンテンツ戦略の方向性（AEO・LLMO — 2026年7月時点の最優先方針）

Google検索のSEOだけでなく、ChatGPT・Claude・Gemini・Perplexity・Google AI Overviewなどの**AI検索・回答エンジンに引用されること（AEO / LLMO）**を狙う。優先順位は次のとおり。

1. **記事数を増やす**（長期目標：100記事）— 網羅性がAI引用の前提になる
2. **記事同士を網のように内部リンクする** — 関連記事・既存記事への双方向リンクを常に意識する
3. **AIが引用しやすい書き方にする**（下記チェックリスト）

### AI検索最適化チェックリスト（毎記事・毎H2で意識すること）
- **結論を記事冒頭に書く**（このサイトの`section-conclusion`は既にこの型。継続すること）
- **各H2セクションの最初に、要点を2〜3文で簡潔にまとめる**（詳細説明はその後に続ける。AIは冒頭の要約文を引用しやすい）
- **比較表を1つ以上入れる**（`.compare-table`）。同じ記事内・記事間で使い回さず、記事ごとに軸の異なるオリジナル表にする
- **FAQを8問以上**（`.blog-faq-item`）。Q＆Aの単純な一問一答形式を保つ（AIがそのまま引用しやすい）
- **箇条書きを積極的に使う**（「主な用途は／・◯◯／・◯◯」のような列挙形式。地の文の羅列より箇条書きの方が引用されやすい）
- **専門用語は簡潔に定義してから使う**（「Claude Codeは、Anthropicが提供する〜です」のように、初出時に一文で定義する）
- **一次情報・体験ベースの内容を含める**（マダナイ？自身の実践・使用経験に基づく記述。単なるツール紹介で終わらせない。下記「実践記事」参照）
- **事実と意見を区別して書く**（「〜とされています」「〜という傾向があります」と、断定できない情報は明示的にヘッジする。既存の書き方の慣習を継続）
- **根拠のある情報は公式情報を確認したうえで反映する**（Claude Code・ChatGPT等、変化の速い製品の料金・仕様は必ずWeb検索で執筆時点の情報を確認し、「執筆時点の情報です。最新情報は公式サイトでご確認ください」と明記する）
- **関連記事への内部リンクを設置する**（新記事同士・新記事↔既存記事の双方向リンクを必ず設置。第9章「サイト更新」の内部リンク要件と重複するが、AEOの観点でも重要）
- **見出しは「◯◯とは？」のように、読者が答えを即座に得られる具体的な形にする**（「便利なAIとは？」のような曖昧な見出しではなく「Claude Codeとは？」のように固有名詞・具体名を使う）
- **画像・スクリーンショットが用意できる場合は積極的に使う**（実際の操作画面、プロンプト、生成結果など。現状は該当する自社アセットがない記事では画像なしとしているが、今後実践記事を作る際は screenshot を優先的に用意する）

### 「実践記事」という強い切り口（他社が書けない一次情報）
単なるツール紹介記事より、マダナイ？自身の実体験に基づく記事がAI検索・Google検索の両方で強い。以下のような切り口を今後のネタとして優先的に検討する。
- 「Claude Codeで実際にマダナイ？のホームページを制作した流れ」
- 「ChatGPTだけでブログ記事を作ってみた結果」
- 「AIで業務アプリを開発した手順」
- 「ホームページ制作会社がClaude Codeを導入して変わったこと」
- 「AI研修を実施するときに企業からよくある質問」

こうした記事を書く際は、架空の実績・レビューを作らないこと（既存の品質ルールを厳守）。実際に行った作業・確認できる事実のみを一次情報として記述する。

## 1. 記事ファイル本体
- `blog/` 配下に新規HTMLファイルを作成。既存記事（例: `blog/ai-shift-scheduling.html`）を丸ごとコピーして流用し、CSS・header・footer・script は変更しない。
- 公開日は**実際にその記事を作成・公開する当日の日付**を使用する（架空の日付は禁止）。以下をすべて同じ日付で統一する：
  - 画面表示の公開日（`.blog-pubdate time`）
  - `<time datetime="...">`
  - BlogPosting JSON-LD の `datePublished`
  - BlogPosting JSON-LD の `dateModified`
  - sitemap.xml の該当 `<lastmod>`
- `.blog-category` バッジは既存のAI関連記事群と同じ表記 `AI活用・業務効率化` を使う（blog.html側のカテゴリー見出し表記 `AI導入・業務効率化` とは意図的に別表記になっている既知の差異。今後統一する場合は既存記事も含めて一括で直すこと。片方だけ直さない）。
- FAQは既存記事と同じ `.blog-faq-item`（`<h3>`+`<p>`のみ、開閉ボタンなし）の形式を使う。FAQPage構造化データは既存ブログ記事では使用していない（BreadcrumbList + BlogPostingの2つのみ）ので、明示的な指示がない限り追加しない。
- 画像を使う場合、`assets/images/` 内に既存の未使用画像（例: 商品・サービスの実物マーケティング画像）がないか先に確認し、あれば流用する。新規画像が必要な場合は必ずユーザーに確認する。

## 2. サイト全体への反映（毎回必須）
- **blog.html**
  - 「すべての記事」の該当カテゴリーグループへカードを追加
  - 該当カテゴリーの `category-count`（「カテゴリーから探す」セクション）を+1
  - 「新着・おすすめ記事」（3枚固定グリッド）へ、必要に応じて最も話題性の近いカードと入れ替え（裁量判断は必ず報告する）
- **index.html**
  - トップページの「お悩み解決ブログ」欄（`.home-blog-grid`、3枚固定グリッド）を、必要に応じて更新（HP制作2枚＋AI系1枚などの構成バランスを維持しつつ、最新のAI系記事に差し替えるのが基本方針）
- **関連記事（新記事側）**：`.related-grid` に1〜3件、内容が近い既存記事へのリンクを設定
- **内部リンク最適化**
  - 新記事の本文中から既存記事へ自然な文脈でリンク（最低2〜3件）
  - 既存の関連記事側の本文にも、新記事への内部リンクを1〜3件、自然な文脈で追加（一方向だけにしない）
- **sitemap.xml**
  - 新規URLを `<url>` として追加（`lastmod`は実際の公開日、`changefreq: monthly`、`priority: 0.7` が既存記事の基準値）
  - `blog.html` 自体の `<lastmod>` も、実際に編集した日付へ更新
  - 追加後、既存URLが重複・欠落していないかXMLパーサーで構文検証する
- **robots.txt**：新記事URLがブロックされていないか確認（現状 `Allow: /` のみなので通常は問題ないが、必ず確認して報告する）

## 3. SEO・品質チェック（毎回必須）
- title・meta description・canonical・OGP（og:image/width/height/url/locale）・Twitter Card をすべて設定
- BreadcrumbList・BlogPosting の JSON-LD が有効なJSONであること、画面表示（パンくず・タイトル）と内容が一致していることを確認
- title・H1がサイト内の既存ページと重複していないか確認
- 画像には alt 属性を設定
- 本文中・カード内・関連記事欄のリンクにリンク切れがないか確認（Playwrightでの実機チェック推奨）
- 「やってはいけない○○」「知らないと損」等の量産型タイトルパターンは禁止

## 4. 検証（毎回必須）
- Playwrightで最低限 PC／タブレット／スマホの3サイズを確認：
  - 各ページでHTTP 200、H1が1つ、横スクロールが発生していないこと
  - JSON-LDのパース可否
  - モバイルメニューの開閉動作
  - コンソールエラーが発生していないこと

## 5. Git運用
- 上記すべてを実施したうえで、**commit・pushは行わずに停止**し、変更内容と検証結果をユーザーへ報告する。
- ユーザーから明示的に「コミットプッシュ」等の指示があった場合のみ、その回に限り commit・push する（毎回の承認が必要。一度の承認が今後の全ラウンドを自動承認するものではない）。
- pushする場合は `origin main` を対象とする（このプロジェクトではユーザーの明示的指示により一貫して `main` ブランチを使用している）。
